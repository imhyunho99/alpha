# 2026-08-23 — Autopilot 구축과 모델 재검증

한 세션에서 v3.2.0(Autopilot)과 v3.3.0(공백 재생)까지 진행한 기록. 커밋 36개, 테스트 19개 → 288개.

## 무엇을 만들었나

사용자가 자본금을 넣고 **온도(1~10) 하나만** 정하면 개입 없이 굴러가는 모의 자동 운용.

설계의 축은 함수 하나다.

```python
def step(account, profile, tickers, prices, clock, journal, prob_fn, score_fn, horizon, last_rebalance)
```

시계와 가격 소스를 주입받으므로 **백테스트와 실시간이 같은 코드로 돈다.** 이 결정이 나중에 세 번 값을 했다 — 백테스트, 공백 재생, 그리고 온도별 곡선 미리보기가 전부 같은 엔진을 재사용한다.

실계좌 경로는 만들지 않았다. `autopilot/` 이 `brokers/` 를 import 하지 않는 것이 불변식이고 테스트가 강제한다.

## 왜 백테스트를 엔진의 일부로 만들었나

착수 전 기존 성능 수치를 검증했더니 쓸 수 없었다. `performance_results_v2.csv` 199종목 중 43개가 정확도 1.0인데 precision·recall 도 1.0 — 홀드아웃 마지막 20%가 통째로 상승장이라 "항상 오른다"가 다 맞은 것이었다. `backtest_data.json` 은 빈 배열이었다. 포트폴리오 수준 백테스트가 실행된 적이 없었다.

검증되지 않은 예측기에 자본의 재량권을 넘기는 기능을 만들고 있었으므로, 백테스트를 사후 검증 도구가 아니라 실행 모드로 설계했다.

## 이 레포에서 세 번 반복된 착각

전부 "모델이 좋다"로 보였고 전부 아니었다.

| | 증상 | 실제 원인 |
|---|---|---|
| 1 | 정확도 100% 43종목 | 홀드아웃 구간이 상승장 |
| 2 | 백테스트 +3,676% | 모델이 시험 기간을 학습 + 생존 편향 |
| 3 | IC 0.102 | 원시 가격 단위로 종목을 식별 |

3번이 가장 미묘했다. `SMA_20=500`(애플)과 `SMA_20=0.001`(잡코인)은 모델에게 지문이다. 거기에 섹터·산업·시총·베타가 붙으면 종목이 거의 특정된다. 정규화하고 식별 컬럼을 빼자 IC 가 0.102 → 0.049 로 반토막 났다.

## 정직한 성능 수치

`alpha_server/benchmark.py` — walk-forward 8폴드, 학습 꼬리 20일 퍼지, 시험 구간 2025-03 ~ 2026-08, 138종목.

| 후보 | IC 평균 | ICIR | 10분위 스프레드 |
|---|---:|---:|---:|
| always_up | — | — | -0.06% |
| momentum(20일) | -0.016 | -0.07 | -1.10% |
| norm13 (정규화 17→13) | 0.049 | 0.21 | +0.67% |
| current17 (원시 가격) | 0.102 | 0.48 | +2.40% |
| **voting76 (채택)** | **0.095** | 0.47 | **+2.87%** |

`norm13` 과 `voting76` 의 대비가 핵심이다. 둘 다 정규화됐는데 IC 가 0.049 vs 0.095 다. 즉 `current17` 의 0.102 는 식별이었고 `voting76` 의 0.095 는 패턴이다. **정규화된 상태로 신호를 내려면 피처가 그만큼 필요했다.**

`always_up` 과 `momentum` 을 후보에 넣은 것이 결정적이었다. 그 기준이 없었으면 IC 0.102 를 보고 "잘 된다"고 넘어갔을 것이다.

20일 지평에서 모멘텀은 **역방향**이다(평균회귀). 회전이 빠른 고온도 설정이 이 지평에서 구조적으로 불리할 수 있다.

## 모건스탠리 퀀트 모델 건

사용자가 "GitHub 에 유명한 데서 퀀트 모델을 무료로 다 풀었다"고 기억한 건 부분적으로 맞았다.

- [Lag-Llama](https://arxiv.org/pdf/2310.08278) — 모건스탠리 공동 저자, 가중치 공개. 다만 사전학습 도메인에 금융이 없고 **단변량 전용**이라 "900종목 줄 세우기"와 과제 형태가 다르다. zero-shot 주가 예측 성능이 나쁘다는 실측 보고가 있다.
- [Qlib](https://github.com/microsoft/qlib) — **사전학습 가중치를 주지 않는다.** 주는 건 팩터 정의(Alpha158/Alpha360)다.

"유명한 데서 푼 모델을 넣으면 바로 좋아진다"는 시나리오는 없었다. 대신 Qlib 의 팩터 정의를 직접 구현했다(`features_alpha158.py`, 76개, 전부 정규화).

## 배운 것

**같은 일을 하는 코드가 둘이면 하나만 고치게 된다.** 세 번 당했다: `update_all_data` vs `update_all_data_with_progress`, horizon 매핑이 `signals.py` 에만 있던 것, `LivePrices.get` 과 `get_many` 의 배치 여부.

**단위 테스트가 다 통과해도 통합 지점은 깨져 있을 수 있다.** 288개가 전부 녹색인 상태에서 자동 운용이 영원히 아무것도 못 사고 있었다. 백테스트는 다른 경로를 타서 멀쩡했다.

**로그가 없으면 진단이 불가능하다.** 앱 실행 후 잡은 결함 7개 중 5개가 라이브 루프에 계측을 넣은 뒤에 드러났다. 계좌가 비어 있는 것만으로는 "살 게 없었다"와 "안 돌았다"를 구분할 수 없다.

**주기는 모델 지평에 맞춰야 한다.** 20영업일을 예측하는 모델을 5분마다 물어보고 있었고, 그 대가로 "맥을 한 달 내내 켜두라"는 요구가 됐다. 1시간으로 낮추고 공백을 재생하는 쪽이 옳았다.

## 한 달 뒤 볼 것

수익률만 보면 시장이 오르면 다 좋아 보인다. 셋을 보라.

1. **세 계좌의 상대 순위** — 온도가 높을수록 정말 더 벌었나, 더 흔들리기만 했나
2. **MDD 가 백테스트 예측과 맞았나** — 수익 눈금은 못 믿지만 위험 눈금은 기계적이다
3. **`hours_since_tracked`** — 계좌별 가동 공백. 크게 다르면 수익률 비교가 무의미하다

백테스트의 +4,395% 는 잊어도 된다. 모델이 답을 아는 상태로 푼 시험이다. 정직한 기대치는 **IC 0.095, 10분위 스프레드 +2.87%** 이고, 여기서 매매마다 수수료 0.1% + 슬리피지 0.05% 가 빠진다.

# 후속: 무인 운용 하드닝 (v3.3.1)

모의 운용을 시작한 지 몇 시간 만에 서버가 HTTP 연결조차 못 받게 됐다. 그 진단과 수정 기록.

## 증상이 원인을 숨겼다

헬스체크는 응답 없음(연결 거부), 프로세스는 살아 있고, CPU 는 0.1%.

처음엔 "자동 운용 루프가 GIL 을 잡아 막혔다"고 봤다. **틀렸다.** 계산 중이었으면 CPU 가 높았어야 한다. 증상만 보고 추측한 결과였고, 이 세션에서 두 번째 오진이었다(첫 번째는 10분위 스프레드 -703% 를 모델 문제로 본 것 — 실제로는 스테이블코인 데이터 오염).

## 실제 원인: 파일 디스크립터 고갈

```
launchd 기본 fd 한도   256
실제 열린 fd           542  →  25분 뒤 1122
누수 지점              ~/Library/Caches/py-yfinance/tkr-tz.db   226 → 694개
```

yfinance 가 `download` 마다 타임존 캐시 SQLite 핸들을 열고 닫지 않는다. 907종목을 받자 한도를 넘겼고, 그때부터 **모든 파일 열기가 실패**했다.

로그의 세 에러가 전부 같은 뿌리였다.

| 증상 | 실제 |
|---|---|
| `DNSError: Could not resolve host` | 소켓을 못 염 |
| `SSLError: cert verify locations cacert.pem` | CA 파일을 못 염 |
| `OperationalError: unable to open database file` | SQLite 를 못 염 |
| 배치 78/100 → 29/100 → 0/100 | 레이트 리밋이 아니라 fd 고갈 |
| HTTP 연결 거부 | `accept()` 가 EMFILE |

**진단 방법**: `lsof -p PID | awk '$5=="REG"{print $9}' | sed 's|.*/||' | sort | uniq -c | sort -rn` 로 무엇이 새는지 즉시 보인다. `launchctl limit maxfiles` 로 한도 확인. py-spy 는 macOS 에서 root 가 필요해 못 썼다.

## 로그를 읽다 걸린 치명적 결함

fd 를 고치고 로그를 보다가 `aggressive` 평가액이 1,638,497원으로 찍힌 것을 발견했다. 실제 equity 는 9,999,996원이었다. 표시 문제가 아니었다.

`market_value()` 는 **가격을 받은 종목만** 합산한다. 일부 가격이 빠지면 equity 는 급락하는데 `borrowed` 는 그대로다.

```
정상   equity 9,999,996 / gross 11,402,044 → margin 0.877   안전
누락   equity   236,449 / gross  1,638,497 → margin 0.144   청산 임계 0.25 미만
```

**레버리지 계좌가 네트워크 오류 한 번에 전량 청산될 수 있었다.** 모의라 금전 손해는 없지만 한 달 관찰 데이터가 통째로 오염된다.

이제 보유 종목 가격이 하나라도 없으면 아무 판단도 하지 않고 다음 사이클로 넘긴다. 보유가 없을 때는 가드가 걸리지 않아 신규 진입은 계속 가능하다.


## 도구 사용 결과

**conductor 는 값을 했다.** 하드닝 세 갈래(yfinance 세션 / 다운로드 백오프 / 헬스 계측)가 서로 독립적이라 병렬로 끝냈다. 슬레이브 하나는 배정 범위를 지켜 `main.py` 의 이중 청킹 문제를 고치지 않고 **보고만 했다** — 옳은 판단이었다.

주의: `conductor send` 에 빈 줄이 섞인 긴 프롬프트를 넘기면 TUI 가 중간에 제출해버리고 나머지가 입력창에 남아 슬레이브가 멈춘다. `conductor doctor sN` 이 알려주고, `tmux send-keys -t <세션>:sN Enter` 로 복구한다. 프롬프트를 한 줄로 보내면 예방된다.

**runahead 는 이 작업에서 도움이 안 됐다.** 누적 3,302,512 토큰($3.17), 미스율 100%, 산출물 없음. 다섯 번 시도 중 세 번은 슬레이브가 파일을 쓰는 중이라 dirty tree 로 거부됐고, 한 번은 큐가 빈 채 종료, 한 번은 1.13M 토큰을 쓰고 이미 고친 문제를 추측했다.

구조적으로 안 맞는 이유가 있다. runahead 는 "방금 끝낸 작업 다음에 뭘 할지" 추측하는데, 이 세션은 **다음 작업이 이전 작업의 실패에서 나왔다.** fd 고갈은 예측 가능한 후속이 아니라 운영 중에 터진 것이었고, 벤치마크 결과도 돌려보기 전엔 몰랐다.

## 배운 것

**증상만 보고 원인을 추측하면 틀린다.** 이 세션에서 두 번 틀렸고, 두 번째는 CPU 0.1% 라는 명백한 반증이 눈앞에 있었는데도 틀렸다. 숫자가 이상하면 모델을 의심하기 전에 **입력과 자원**을 봐야 한다.

**관찰 가능성이 없으면 아무것도 못 고친다.** fd 누수도, 잘못된 청산 위험도, 로그에 숫자를 찍기 시작한 뒤에야 보였다. 특히 잘못된 청산은 로그를 눈으로 읽다가 우연히 걸린 것이다 — 계측이 없었으면 한 달 뒤에 "왜 이 계좌만 망했지?" 하고 끝났을 것이다.

# 후속 2: 가격 누락 (v3.3.2)

v3.3.1 을 릴리즈하고 세션을 닫으려던 참에 로그에서 이게 보였다.

```
[aggressive] 건너뜀(가격 누락 9/15종목) · 평가 3,158,746원
             실제 equity 는 9,999,972원
```

## 가드가 결함을 드러냈다

몇 시간 전에 넣은 "가격 모르면 판단하지 않는다" 가드가 없었다면, equity 가
반토막으로 계산돼 `margin_ratio` 가 0.25 아래로 떨어지고 **레버리지 계좌가
전량 청산**됐을 것이다. 가드 덕분에 청산 대신 로그가 남았고, 그 로그가 원인을
가리켰다.

한 번은 fd 후유증으로 넘겼는데(재현이 안 됐다) 다음 사이클에 더 나빠져서
재발했다(7/15 → 9/15). **정황은 증거가 아니다.**

## 원인: 배치의 부분 성공

```python
if raw is None or raw.empty:      # 청크 전체가 실패했을 때만 폴백
    ...개별 조회...
```

배치가 부분 성공하면 그냥 넘어갔다. `period="1d"` 는 휴장일이나 상장 초기
종목에서 봉이 비거나 `Close` 가 NaN 인데, 그런 종목은 `continue` 로 조용히
버려졌다. 토요일 새벽이라 미국장이 닫혀 더 두드러졌다.

**수정**: 배치에서 값을 못 얻은 종목만 모아 개별로 다시 묻는다. 개별 조회의
`period` 는 `1d` → `5d` 로 바꿔 휴장일에도 마지막 종가를 얻는다.

```
수정 전   보유 15종목 중 9개 누락, equity 3,158,746원
수정 후   150/150 확보, 누락 0,   equity 9,999,972원
```

## 배운 것

**방어와 수정은 둘 다 필요하다.** 가드는 증상(잘못된 청산)을 막았고, 이
커밋이 원인(부분 성공 미처리)을 막았다. 가드만 있었으면 계좌가 한 달 내내
건너뛰기만 했을 것이고, 가드가 없었으면 첫날 밤에 청산됐을 것이다.

**부분 실패는 전체 실패보다 위험하다.** 전부 실패하면 폴백이 걸리고 눈에도
띈다. 절반만 실패하면 코드는 성공으로 처리하고 숫자만 조용히 틀어진다.
